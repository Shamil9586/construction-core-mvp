# Проверенный сценарий

Автотест: `tests/workflow.test.ts`. Он запускает настоящий NestJS HTTP server, выполняет запросы через fetch и записывает данные в PostgreSQL WASM engine (PGlite). Это API E2E, не браузерный E2E.

1. Применить миграции дважды, seed дважды; проверить идемпотентность.
2. РП создаёт объект и назначает себя/субподрядчика.
3. Создать армирование 20 т и бетонирование; связать FINISH_TO_START с приёмкой.
4. Внести 10 т: проверить 50%, линейный план и RED. Устаревшая version → 409.
5. Довести до 20 т; предъявить СК. Попытка РП принять → 403.
6. СК открывает критическое замечание. Проверка допуска false; начать бетонирование → 400.
7. РП отмечает устранение; блокировка остаётся.
8. СК проверяет устранение. Приёмка без фото → 400. Загрузить фото, принять.
9. РП видит разрешение и начинает бетонирование.
10. ПТО создаёт пакет. Неполный пакет не проходит validation.
11. Добавить материал, партию, паспорт и файл; создать АОСР DRAFT, подтвердить ПТО.
12. Отметить пакет READY, передать СДО. Повторная передача со старой version → 409.
13. СДО вводит 1 000 000 ₽. Закрытие сверх суммы → 400.
14. Закрыть 1 000 000 ₽; повторить idempotencyKey — та же запись.
15. Dashboard: факт месяца +1 000 000 ₽, потенциал −1 000 000 ₽.
16. Проверить основные audit actions и две записи WorkProgress.
17. Подрядчику запрещены финансовая панель и mutations. Межпортальный FK отклонён, чужому РП объект недоступен. UPDATE AuditLog запрещён триггером.

Для проверки через UI повторить процесс на тестовом сервере: роли переключаются через «Выйти» → новый mock-вход. Файл для документа выбирается в форме, материал добавляется в «Материалы». Вкладки объекта используют те же API. В текущей среде браузер блокирует localhost, поэтому ручное прохождение этих экранов ещё требуется.
