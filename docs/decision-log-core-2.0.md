## 1. RED escalation (дни до эскалации)

**Текущие значения**: Core — 3 / 7 дней (`escalate_technical_days`,
`escalate_director_days`, `packages/domain/index.ts: defaultRisk`); ERP — 7 / 14
дней (`RiskSettings.escalateToTechDirectorAfterDays`/`escalateToGeneralDirectorAfterDays`).

**Решение**: оставить значения Core (3 / 7) как значения по умолчанию.

**Причина**: оба набора значений — валидные бизнес-политики без объективного
критерия "правильности"; более быстрая эскалация Core — консервативный выбор
в пользу раннего сигнала о проблеме, а не ошибка. Менять умолчания без
конкретного запроса заказчика — решение "по собственному усмотрению", что
прямо запрещено принципом задачи. Нет ни одного теста/сценария, который бы
показал, что значения 3/7 дают неверный бизнес-результат.

**Tenant-configurable**: да, уже сейчас — `POST /settings/risk` (permission
`ADMIN_DICTIONARIES`, `dictionaries.controller.ts`) позволяет ADMIN каждого
тенанта задать свои `escalateTechnicalDays`/`escalateDirectorDays` независимо
от глобального умолчания. Изменение не требуется.

**Изменение кода**: нет. **Тест**: не требуется (значения уже покрыты
`EscalationService`-тестом в `tests/domain.test.ts`, структура не менялась).

## 2. staleDays (срок актуальности факта)

**Текущие значения**: Core — 7 дней (`stale_days`); ERP — 10 дней
(`staleProgressAfterDays`).

**Решение**: оставить значение Core (7 дней).

**Причина**: та же логика, что и в п.1 — оба значения обоснованы, нет
объективного основания предпочесть ERP. 7 дней — более консервативный
(быстрее помечает объект как "нет данных" / GRAY), что соответствует духу
business-rules.md ERP же ("честный сигнал ГД, что данные протухли") — если
что-то менять, то в сторону строгости, а не мягкости, но и это не требуется:
значение уже настраиваемое.

**Tenant-configurable**: да, уже сейчас — то же `POST /settings/risk`
(`staleDays` поле, `min(1).max(90)`).

**Изменение кода**: нет. **Тест**: не требуется.

## 3. isOverperformed (сигнал "факт превышает план")

**Необходимость**: да, сигнал нужен явно, а не только "молчаливо" через
клампинг `progressPercent` в `[0,100]` — без него РП/ГД не может отличить
"ровно выполнено" от "перевыполнено", что важно для планирования ресурсов и
для честности отчётности (Core прежде показывал 100% в обоих случаях
неразличимо).

**Решение**: добавить `isOverperformed: boolean` как транзиентный (не
персистентный) сигнал в ответ `POST /works/:id/progress` — вычисляется
каждый раз заново, как и `progressPercent`/`scheduleStatus`, ничего не
пишется в БД, схема не менялась.

**Изменение** (реальный код, единственное на этом этапе):
- `packages/domain/index.ts`: `ProgressCalculationService.isOverperformed(actual, planned)`
  — новый метод, `calculate()` не тронут (обратная совместимость всех
  существующих вызовов — `service.ts`, `read-service.ts`, `PotentialClosingService`).
- `apps/backend/src/service.ts`, `progress()`: ответ дополнен полем
  `isOverperformed`.

**Тест**:
- `tests/domain.test.ts` — юнит-тест метода (границы: меньше/равно/больше плана).
- `tests/core-2.0-decisions.test.ts` — HTTP-тест `POST /works/:id/progress`,
  подтверждающий `isOverperformed: true` при факте > плана и `false` в двух
  остальных случаях, плюс что `progressPercent` по-прежнему клампится в 100
  (сигналы независимы).

## 4. RBAC: OBJECT_MANAGE_CONTRACTORS vs OBJECT_EDIT

**Проверено** (не только наличие permission, но фактическое использование в
коде — `grep` по всем контроллерам/`service.ts`):

- `OBJECT_MANAGE_CONTRACTORS` в Core **не существует** как permission вообще.
- `OBJECT_EDIT` **присвоен** ролям PROJECT_MANAGER/TECHNICAL_DIRECTOR/ADMIN
  (`packages/domain/index.ts`, `grants`), но **не используется НИ ОДНИМ**
  `requirePermission(...)` вызовом ни в одном контроллере — это мёртвый
  permission, потому что в Core вообще нет endpoint'а редактирования объекта.
- Управление подрядчиками объекта после создания (assign/remove) — тоже
  отсутствует как endpoint (зафиксировано в Этапе 1, `docs/core-2.0-regression-map.md`,
  раздел 1, MISSING_BEHAVIOR).

**Вывод**: сегодня в Core **нет фактического over-broad доступа** к
разделению — нечего "разделять" в живом коде, потому что endpoint, который
эту разницу продемонстрировал бы (тот самый, что ERP чинил через
`OBJECT_MANAGE_CONTRACTORS`), в Core не реализован. Добавлять permission,
который сразу же станет вторым мёртвым permission без единого места
использования, — не решение проблемы, а имитация её решения; это
противоречит принципу "изменение должно закрывать конкретный выявленный
gap" (закрывать нечего, пока gap — отсутствие самого endpoint'а, а не
чрезмерность прав).

**Решение**: код сейчас не менять. Предварительное решение на будущее
(фиксируется здесь, чтобы не повторить дефект ERP при реализации): когда
управление подрядчиками объекта после создания будет реализовано (Core 2.0
Phase 2, см. Этап 1), оно **обязано** использовать отдельный, новый permission
`OBJECT_MANAGE_CONTRACTORS`, а не `OBJECT_EDIT` и не `OBJECT_CREATE` — ровно
так, как это в итоге сделал ERP после своего инцидента (verification-report,
"Defects found... #1").

**Изменение кода**: нет (осознанно). **Тест**: не применимо — нет кода для
тестирования до реализации endpoint'а в Phase 2.

## 5. Construction Control workflow: блокирует ли READY_FOR_VERIFICATION финальную приёмку

**Текущее поведение Core** (проверено, `service.ts: inspectionAction('accept')`):
да, блокирует — `accept` отклоняется (400), если у проверки есть **любое**
замечание любой критичности (LOW/MEDIUM/HIGH/CRITICAL) не в статусе `CLOSED`,
включая `READY_FOR_VERIFICATION`. Требуется явный `issues/:id/verify` от СК
для каждого замечания, прежде чем приёмка станет возможна.

**Поведение ERP** (business-rules.md §5, verification-report "Defects found...
#2"): только открытое `CRITICAL`-замечание блокирует приёмку;
`READY_FOR_VERIFICATION` (в т.ч. по CRITICAL) явно **не блокирует** —
приёмка и верификация могут идти в одной транзакции.

**Решение**: оставить текущее поведение Core (блокирует до явной верификации,
независимо от severity) как решение Core 2.0.

**Причина**: это более консервативное правило (требует, чтобы каждое
замечание — не только критическое — было явно проверено СК перед итоговой
приёмкой), не дефект. Смена на правило ERP была бы содержательным изменением
бизнес-логики без запроса на это и без выявленного инцидента, который бы её
оправдывал (в отличие от значений порогов в п.1-2, здесь при этом остаётся
несогласованность внутри самого Core — технологическая блокировка следующей
работы смотрит только на `CRITICAL`-замечания (`read-service.ts` blockers), а
приёмка той же работы — на любое замечание; это стоит иметь в виду как
внутреннюю асимметрию, но не как повод менять поведение сейчас без отдельного
решения).

**Изменение кода**: нет. **Тест**: уже закреплено — сценарий F,
`tests/regression-erp-parity.test.ts` (Этап 1), явно проверяет, что
незакрытое замечание (в т.ч. не-CRITICAL) блокирует `accept` до `verify()`.

## 6. Optimistic concurrency

**Проверено**: `version` (int, default 1) + `checkVersion()` (409 при
несовпадении) реализованы и **фактически используются** на каждом изменяемом
через API ресурсе: `works` (start/progress), `inspections` (accept/reject),
`issues` (resolve/verify), `executive_documents` (approve), `executive_packages`
(ready/transfer-sdo), `sdo_cases` (calculate, через `financial-closings`),
`risk_settings` (`settings/risk`). Проверено построчно по `service.ts` и
контроллерам — пропусков не найдено.

Единственный ресурс с колонкой `version` в схеме, но без реального мутирующего
endpoint'а — `objects` (нет edit-эндпоинта вовсе, см. п.4) — там защищать
физически нечего, это не пробел в конкурентной защите, а следствие отсутствия
самой функции редактирования.

**Решение**: ничего не добавлять — механизм уже присутствует везде, где есть
реальная мутация.

**Изменение кода**: нет. **Тест**: уже закреплено существующими тестами —
`tests/acceptance.test.ts` ("Two sessions race on version N: exactly one
update and one conflict" — явный параллельный race-тест) и множественные
409-проверки в `tests/workflow.test.ts`/`tests/regression-erp-parity.test.ts`.
