# Core 2.1 — Architecture Plan (только план, implementation не выполнялся)

Источники: `docs/core-2.0-regression-map.md`, `docs/domain-parity-core-erp.md`,
`docs/decision-log-core-2.0.md` — конкретно, накопленный список из 7 пунктов
MISSING_BEHAVIOR + одно уже решённое расхождение бизнес-правила (severity/
READY_FOR_VERIFICATION, изменений не требует, в план не включено).

Ограничения этого документа: не создавать новые таблицы, не менять
архитектуру (raw `pg` + SQL-миграции + PGlite остаются), не выполнять
implementation. Ниже — план, не код.

## 1. Приоритеты Phase 2

| # | Пункт (из decision log) | Приоритет | Почему |
|---|---|---|---|
| 1 | Управление подрядчиками объекта после создания (assign/remove + `?contractorId=` фильтр) | **P1** | Прямое соответствие реальному процессу (субподрядчики меняются по ходу объекта); низкий риск — таблица `object_contractors` уже есть, только API поверх неё. Логично делать вместе с п.2 (обе используют одну RBAC-развилку). |
| 2 | `OBJECT_MANAGE_CONTRACTORS` permission | **P1** | Не имеет смысла отдельно от п.1 — это permission именно для endpoint'а из п.1. Делать одним PR/итерацией с п.1, не раньше и не отдельно. |
| 3 | Object edit endpoint (нет вообще) | **P1** | Высокая продуктовая ценность (сейчас нельзя исправить опечатку в адресе объекта или продлить срок) при умеренном риске — `version`-конкурентность уже есть в схеме, шаблон реализации (`checkVersion`+`transaction`) уже есть в `service.ts` для других сущностей. |
| 4 | Частичная приёмка объёма (`acceptedQuantity`) | **P2** | Существенная бизнес-ценность (соответствует реальной практике СК), но задевает `PotentialClosingService`, `PtoPackageValidationService`, `WorkTransitionPolicy` и dashboard одновременно — требует отдельного decision-log прохода перед реализацией, не просто "добавить поле". |
| 5 | Многоработные пакеты ИД / SdoCase 1:N | **P3** | Ломает текущие `UNIQUE`-инварианты (`sdo_one_per_work`, `sdo_cases_unique`), на которые опираются существующие тесты (`workflow.test.ts`, `regression-erp-parity.test.ts`). Нет доказанного спроса на батчинг нескольких работ в одном пакете ИД для MVP — приоритет ниже, пока не появится конкретный кейс от пользователя. |
| 6 | `dictionary_items` (мёртвая таблица) | **P4** | Требует сначала бизнес-решения "использовать или удалить", а не технической работы. Ничего не сломается, если отложить бессрочно. |
| 7 | `work_templates` (мёртвая таблица) | **P4** | Аналогично п.6 — решение важнее реализации. |

Рекомендуемый порядок работы: **(1+2) → 3 → 4 → 5**, пункты 6-7 — по
отдельному запросу пользователя в любой момент, независимо от остальных.

## 2. Изменения, требующие миграции БД

Ни одно из следующего не требует **новых таблиц** — только `ALTER TABLE` на
существующих:

| Пункт | Миграция |
|---|---|
| 1. Contractor management post-creation | Не требуется, если снятие подрядчика — обычный `DELETE`. Если решить делать soft-remove (сохранять историю "кто и когда снял подрядчика" отдельно от `audit_logs`) — потребуется `ALTER TABLE object_contractors ADD COLUMN removed_at timestamptz` (решение отдельно, не обязательно). |
| 3. Object edit | Не требуется — `objects.version` уже есть в схеме (`infra/001_initial.sql`), просто не используется ни одним endpoint'ом сейчас. |
| 4. Частичная приёмка | **Да** — `ALTER TABLE inspections ADD COLUMN accepted_quantity numeric(20,4)`. Открытый вопрос архитектуры: хранить агрегат ещё и на `works` (как в ERP — денормализовано) или считать его на лету join'ом `inspections` (как Core уже делает для `progressPercent`/`scheduleStatus`/funnel-бакетов в `read-service.ts`) — второе консистентнее с уже принятым в Core паттерном "вычислять, а не дублировать" и не требует колонки на `works` вообще. Рекомендация: только `inspections.accepted_quantity`, без дублирования на `works`. |
| 5. Многоработные пакеты ИД | **Да**, две части: (а) `ALTER TABLE executive_packages ALTER COLUMN object_work_id DROP NOT NULL` (пакет перестаёт быть привязан к одной работе — работа определяется через документы пакета, как в ERP); (б) пересмотр уникальных индексов на `sdo_cases`: заменить `sdo_cases_unique (tenant_id, executive_document_package_id)` на составной `(tenant_id, executive_document_package_id, object_work_id)`, аналогично ERP `@@unique([executiveDocumentPackageId, objectWorkId])`. Это ломающая миграция для существующих данных с `NOT NULL` — нужен явный план миграции существующих строк (не просто `ALTER`), включая проверку, что `002_invariants.sql`'s `sdo_one_per_work` не конфликтует с новой моделью. |
| 6-7. `dictionary_items`/`work_templates` | Не требуется технически (таблицы уже есть). Если решение — "начать использовать", миграция нужна только для seed-данных, не для схемы. |

## 3. Изменения, требующие API

| Пункт | API |
|---|---|
| 1. Contractor management | `POST /objects/:id/contractors` (вынести из `createObject` в отдельный метод, с 409-guard, если контрактор уже назначен), `DELETE /objects/:id/contractors/:contractorId` (с 409, если есть работы этого подрядчика на объекте — прямая копия проверки из ERP `п.3` integrity-fix), `GET /objects?contractorId=` — добавить фильтр в `ReadService.snapshot` / `ObjectsController.objects`. |
| 2. OBJECT_MANAGE_CONTRACTORS | Новый `Permission` в `packages/domain/index.ts`, назначить PROJECT_MANAGER/TECHNICAL_DIRECTOR/ADMIN, использовать в `requirePermission()` двух endpoint'ов из п.1 — **не** в связке с `OBJECT_EDIT`. |
| 3. Object edit | `PATCH /objects/:id` — по аналогии с `settings/risk` (`checkVersion` + `transaction` + `audit`). Открытый вопрос: какие поля редактируемы (скорее всего `name`/`address`/`customerName`/`organizationName`/`plannedFinishDate`; `projectManagerId` — отдельная RBAC-развилка, вероятно только TECHNICAL_DIRECTOR/ADMIN, не сам РП, чтобы РП не мог передать объект себе или снять с себя ответственность; `contractValue` — вероятно НЕ редактируется постфактум ради целостности финансового следа, но это бизнес-решение, не техническое). |
| 4. Частичная приёмка | `POST /inspections/:id/accept` — DTO дополняется опциональным `acceptedQuantity` (по умолчанию = текущему `actualQuantity` работы, чтобы не менять поведение существующих вызовов без этого поля — обратная совместимость). `read-service.ts`: `PotentialClosingService`/funnel должны использовать `accepted_quantity`, а не булево "принято/не принято". `WorkTransitionPolicy` — решить, разблокирует ли частичная приёмка последующую работу (по умолчанию логично: нет, только полная приёмка = `acceptedQuantity >= plannedQuantity`; это отдельное решение, не техническая деталь). |
| 5. Многоработные пакеты | `POST /executive-packages` — перестаёт принимать `objectWorkId`, вместо этого группирует по документам (как в ERP: пакет = набор документов, каждый привязан к своей работе). `packageAction('transfer-sdo')` — цикл создания `SdoCase` на каждый уникальный `objectWorkId` среди документов пакета (прямая копия логики `PtoService.transferToSdo` ERP, адаптированная под raw SQL). `packageValidation()` — должен агрегировать по всем работам пакета, а не по одной. |
| 6-7. Справочники | Если решение "использовать" — расширить `DictionariesController`/добавить работу с `work_templates` при создании работы (подстановка `defaultQuantity`). Если решение "удалить/оставить как есть" — API не меняется вообще. |

| Пункт | Frontend |
|---|---|

| 3. Object edit | Форма редактирования объекта (сейчас у объекта в UI нет ни одной формы правки — только создание через Admin/Excel-импорт и просмотр карточки). Нужно решить, где размещать (карточка объекта vs. отдельная вкладка). |
| 4. Частичная приёмка | В форме приёмки СК (`actionForm`) добавить поле "Принятый объём" (сейчас, судя по `workflow.test.ts`, приёмка вызывается без явного ввода объёма — предполагается 100% от предъявленного). |

используется в `main.tsx` (`can(...)`).

## 5. Что нельзя делать до Bitrix24 integration

Ничего из пунктов 1-7 **не требует** реальной Bitrix24-интеграции — все они
работают полностью в рамках `MockBitrixAdapter`/`AUTH_MODE=mock`, как и весь
текущий Core. Отдельно, для полноты (по итогам `domain-parity-core-erp.md`),
явно нельзя делать **до** отдельного разрешения на подключение тестового
Bitrix24-портала:

- Отслеживание жизненного цикла установки (`BitrixInstallation.status`:
  ACTIVE/UNINSTALLED/TOKEN_INVALID) — бессмысленно без реальных
  ONAPPINSTALL/деинсталляции событий от портала.
- Любая автоматическая синхронизация `department`/`departmentName`
  пользователей с оргструктурой Bitrix24.
- Реальная отправка уведомлений в Bitrix24 (`Notification.sentToBitrix`,
  которого сейчас нет в Core, и не должно появляться раньше интеграции).
- Любые изменения `RealBitrixAdapter`, `BITRIX_INSTALL_WEBHOOK_ENABLED`,
  OAuth/refresh-логики — вне scope этого плана независимо от Phase 2.

Это ограничение унаследовано из архитектурных решений исходной задачи
(`docs/status.md`: "Bitrix24: MockBitrixAdapter. Реальный/тестовый портал —
только с отдельного разрешения пользователя") и остаётся в силе для Core 2.1.

## 6. Риски изменения существующей модели

| Пункт | Риск | Смягчение |
|---|---|---|
| 1. Contractor management | Удаление подрядчика с объекта, у которого уже есть работы, может молча "осиротить" `works.contractor_id`-ссылки на UI (сама FK не даст удалить строку `contractors`, но `object_contractors`-снятие — другая операция) | Обязателен 409-guard "нельзя снять, пока есть работы этого подрядчика" — это уже проверенный паттерн из ERP (integrity-fix п.3), просто скопировать инвариант, не изобретать заново |
| 3. Object edit | Если `projectManagerId` editable самим РП — риск, что РП переназначит объект на себя или откажется от ответственности за проблемный объект (обход `objectAccess`-проверки "объект закреплён за другим РП") | Разрешить смену РП только TECHNICAL_DIRECTOR/ADMIN, не самому РП — отдельная RBAC-развилка внутри одного endpoint'а, аналогично тому, как `financial-closings` требует одновременно `SDO_CLOSE`+`FINANCE_EDIT` |
| 4. Частичная приёмка | **Самый высокий риск в списке.** Затрагивает одновременно: `PotentialClosingService` (сейчас предполагает бинарное "принято/не принято"), `WorkTransitionPolicy` (сейчас предполагает бинарное "предшественник принят"), dashboard-агрегаты, и потенциально ломает семантику существующих 31 тестов, которые везде используют `acceptedQuantity == plannedQuantity` неявно | Не трогать существующие сигнатуры (`calculate()` и т.п.) по той же схеме, что и `isOverperformed` в Этапе 2 — добавлять новое поле аддитивно, со значением по умолчанию = полному объёму, чтобы 100% существующих тестов проходили без изменений; отдельный decision-log проход именно по вопросу "разблокирует ли частичная приёмка зависимую работу" ДО написания кода |
| 5. Многоработные пакеты | Ломающая миграция уникальных индексов на боевых данных (если Core 2.0 уже в проде с данными на момент Phase 2) — риск конфликта существующих строк с новым composite `UNIQUE`; также усложняет `packageValidation()`, что может изменить поведение для уже существующих одно-работных пакетов, если рефактор сделан небрежно | Писать миграцию с явной проверкой отсутствия конфликтов перед `ALTER`, и regression-тест, что однора­ботные пакеты (весь текущий 31-тестовый набор) продолжают работать идентично после рефактора |
| 6-7. Справочники | Низкий риск (сейчас не используются, ломать нечего), но добавление использования — это новая функциональность, а не только "починка" существующего, что выходит за рамки принципа "изменение должно закрывать конкретный выявленный gap", если делать без явного запроса пользователя | Не реализовывать без отдельного явного решения — оставить в backlog |
| Общий риск | Любое из P2/P3 изменений может незаметно сломать один из 31 существующих тестов Core 2.0 hardening, если сделано без той же дисциплины (gap → decision → change → test), что использовалась в этой задаче | Требовать полного зелёного прогона `npm test` (сейчас 31/31) + Playwright после каждого пункта Phase 2, не пакетом в конце |
